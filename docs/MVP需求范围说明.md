# AI 软件测试平台 MVP 需求范围说明

> 更新时间：2026年7月10日

## 1. MVP 定位

第一版 MVP 定位为"AI 测试设计平台"，核心验证用户是否愿意把需求文档交给平台，并接受平台生成的测试点和测试用例作为工作起点。

第一版不追求覆盖完整测试管理系统，也不急于做复杂自动化执行。优先把"需求文档到高质量测试用例"的链路做稳定。

## 2. MVP 核心目标

- 支持测试项目创建和基础管理。
- 支持上传需求、原型、接口文档和变更说明。
- 支持 AI 解析需求，输出模块、功能点、业务规则和待确认问题。
- 支持 AI 生成测试点。
- 支持 AI 生成测试用例。
- 支持人工编辑和评审用例。
- 支持用例评审状态管理。
- 支持自动化脚本生成。

## 3. MVP 用户路径

```text
注册/登录
→ 创建项目
→ 上传需求资料
→ 启动 AI 需求解析
→ 查看并确认待确认问题
→ 生成测试点
→ 生成测试用例
→ 人工编辑和评审
→ 生成自动化脚本（可选）
```

## 5. 暂不纳入 MVP 的能力

| 功能 | 暂缓原因 | 优先级 |
|---|---|---|
| 自动化脚本执行 | 需要执行环境、浏览器、CI/CD 和脚本稳定性支撑 | P2 |
| 元素定位自修复 | 依赖页面结构采集和执行失败数据 | P3 |
| 缺陷系统集成 | 需要对接禅道、Jira、TAPD 等外部系统 | P2 |
| 复杂权限体系 | 第一版先验证核心测试设计价值 | P3 |
| 多租户计费 | 不影响第一阶段产品闭环 | P3 |
| 质量预测模型 | 需要历史执行和缺陷数据积累 | P3 |
| 执行记录管理 | 需要完整的测试执行流程支撑 | P2 |
| 缺陷管理 | 需要完整的缺陷跟踪流程 | P2 |
| 测试报告生成 | 需要执行数据和缺陷数据积累 | P2 |
| 知识库检索 | 需要向量数据库支撑 | P3 |
| WebSocket 实时通知 | 可用轮询替代 | P3 |

## 7. 测试用例标准字段

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 用例编号 | 是 | 按模块命名，例如 TC_LOGIN_001 |
| 所属模块 | 是 | 对应需求模块 |
| 功能点 | 是 | 对应具体功能 |
| 用例标题 | 是 | 描述验证目标 |
| 优先级 | 是 | P0/P1/P2/P3 |
| 前置条件 | 否 | 执行前状态 |
| 测试步骤 | 否 | 使用步骤化描述 |
| 测试数据 | 否 | 输入数据或准备数据 |
| 预期结果 | 否 | 可判断的验证结果 |
| 测试类型 | 否 | 功能测试/性能测试等 |
| 实际结果 | 否 | 执行后的实际结果 |
| 执行结果 | 否 | 未执行/通过/失败/阻塞 |
| 自动化标识 | 否 | 待评估/适合/不适合/已自动化 |
| 评审状态 | 否 | 待评审/已通过/需修改 |
| 测试人 | 否 | 执行测试的人员 |
| 测试日期 | 否 | 测试执行日期 |
| 备注 | 否 | 补充说明 |

## 8. AI 输出质量规则

- 需求中没有的信息不能编造成事实。
- 不确定内容必须标记为"待确认"。
- 每条用例必须关联需求来源。
- 测试步骤必须可执行。
- 预期结果必须明确可判断。
- 一条用例只验证一个主要目标。
- 异常、边界、权限和数据一致性场景必须重点覆盖。
- 自动化候选用例应优先选择稳定、高价值、可重复执行的场景。
