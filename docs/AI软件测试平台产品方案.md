# AI 软件测试平台产品方案

## 1. 产品定位

AI 软件测试平台定位为面向测试团队、研发团队和质量管理人员的测试全流程工作台。平台不是单一的“AI 生成测试用例工具”，而是围绕软件测试标准流程，把需求解析、测试设计、用例评审、测试执行、缺陷分析、自动化测试、报告生成和资产沉淀串成完整闭环。

核心目标是让测试工作从“依赖人工经验的文档和表格流转”，升级为“可追溯、可复用、可分析、可自动化的质量工程流程”。

## 2. 建设目标

- 降低需求分析和测试设计的重复劳动。
- 提升测试点、测试用例、异常场景和边界场景覆盖率。
- 建立需求、测试点、测试用例、执行结果、缺陷和报告之间的可追溯关系。
- 通过 AI 辅助生成自动化脚本，提高回归测试效率。
- 通过 AI 分析执行日志、截图和接口响应，提升失败定位效率。
- 沉淀历史需求、用例、缺陷、脚本和经验，形成企业级测试知识库。

## 3. 用户角色

| 角色 | 主要职责 | 平台诉求 |
|---|---|---|
| 测试经理 | 创建项目、制定测试计划、把控质量风险、输出报告 | 需要项目质量全貌、测试进度、缺陷趋势和上线建议 |
| 测试工程师 | 分析需求、设计用例、执行测试、提交缺陷 | 需要高质量测试点、可执行用例、便捷执行记录和缺陷生成 |
| 自动化测试工程师 | 维护自动化脚本、执行回归、分析失败原因 | 需要脚本生成、执行编排、日志分析和定位器维护能力 |
| 产品/业务人员 | 提供需求、确认问题、评审测试覆盖 | 需要查看需求覆盖、待确认问题和测试范围 |
| 开发人员 | 修复缺陷、分析失败、参与回归验证 | 需要准确复现步骤、日志、截图和影响范围 |

## 4. 标准业务流程

```text
创建测试项目
→ 导入需求/原型/接口文档
→ AI 解析需求
→ 生成待确认问题
→ 生成测试点
→ 生成测试用例
→ 人工评审与调整
→ 准备测试数据
→ 执行测试
→ 记录实际结果
→ 生成缺陷
→ 回归验证
→ 输出测试报告
→ 沉淀测试资产
```

平台设计中要保留人工评审节点。AI 生成的需求分析、测试点、测试用例和缺陷建议不能直接作为最终结论，必须经过测试人员确认。

## 5. 测试类型支持

| 测试类型 | 典型场景 | 平台处理方式 |
|---|---|---|
| 首轮全量测试 | 新系统首次测试、无历史用例 | 从需求解析开始，完整生成测试点、用例、数据、报告 |
| 全量复用测试 | 有旧用例但需要重新建立覆盖 | 对比旧用例和新需求，补充遗漏、删除过期项 |
| 回归测试 | 版本变更、缺陷修复后验证 | 根据变更影响筛选已有用例，补充必要新用例 |
| 增量测试 | 新增或修改局部功能 | 识别差异、评估影响范围、生成增量用例 |
| 探索性测试 | 需求不完整或需要经验驱动发现问题 | 生成探索大纲，记录发现，沉淀为正式用例 |

## 6. 核心功能模块

### 6.1 首页驾驶舱

首页用于展示当前质量状态和重点风险，适合测试经理、项目负责人和研发负责人快速判断项目质量。

建议展示指标：

- 当前测试项目数。
- 本周执行用例数。
- 用例通过率和失败率。
- 缺陷总数、严重缺陷数、阻塞缺陷数。
- 自动化覆盖率。
- 高风险模块。
- 待确认需求问题。
- 今日待处理事项。
- AI 质量风险提醒。

### 6.2 项目空间

项目空间是单个测试项目的工作入口。

建议包含：

```text
项目概览
需求资料
测试计划
测试点
测试用例
执行记录
缺陷列表
自动化任务
测试报告
知识沉淀
```

### 6.3 需求解析

需求解析模块负责接收 PRD、FS、Word、PDF、Excel、原型截图、接口文档和变更说明。

AI 输出内容：

- 系统模块。
- 功能点。
- 业务规则。
- 输入和输出。
- 页面或接口。
- 前置条件。
- 异常规则。
- 风险点。
- 待确认问题。

输出字段建议：

| 字段 | 说明 |
|---|---|
| 需求编号 | 用于后续测试点和测试用例追溯 |
| 所属模块 | 需求所属业务模块 |
| 功能点 | 具体功能能力 |
| 业务规则 | 明确的业务判断逻辑 |
| 输入/输出 | 页面字段、接口参数或文件数据 |
| 风险等级 | 高/中/低 |
| 待确认问题 | 需求不清晰或影响测试设计的问题 |

### 6.4 测试设计

测试设计是平台的核心模块，负责从需求生成测试点、测试用例和测试数据。

AI 生成测试点时应覆盖：

- 正常流程。
- 异常流程。
- 边界值。
- 权限控制。
- 数据一致性。
- 状态流转。
- 重复提交。
- 导入导出。
- 审批流。
- 兼容性。

测试用例字段建议：

| 字段 | 说明 |
|---|---|
| 用例编号 | 示例：TC_LOGIN_001、TC_ORDER_001 |
| 所属模块 | 用例对应模块 |
| 功能点 | 用例对应功能 |
| 用例标题 | 清晰描述验证目标 |
| 优先级 | P0/P1/P2/P3 |
| 前置条件 | 执行前必须满足的状态 |
| 测试步骤 | 使用可执行步骤描述 |
| 测试数据 | 明确输入数据 |
| 预期结果 | 可判断的期望结果 |
| 自动化标识 | 是否适合自动化 |
| 需求来源 | 关联需求编号 |
| 评审状态 | 待评审/已通过/需修改 |

### 6.5 用例管理

用例管理负责用例的长期维护和复用。

核心能力：

- 用例新增、编辑、复制、删除。
- 用例版本管理。
- 用例评审流程。
- 按模块、优先级、自动化标识筛选。
- 用例与需求的追溯关系。
- 历史用例复用。
- AI 识别重复用例、遗漏场景和过期用例。

### 6.6 执行中心

执行中心支持手工执行和自动化执行。

执行记录字段建议：

| 字段 | 说明 |
|---|---|
| 用例编号 | 关联测试用例 |
| 执行人 | 实际执行人员 |
| 执行环境 | 测试环境、预发环境等 |
| 执行时间 | 执行日期和时间 |
| 执行结果 | 通过/失败/阻塞/跳过 |
| 实际结果 | 实际观察到的结果 |
| 截图/日志 | 失败证据 |
| 关联缺陷 | 失败后生成或关联的缺陷 |
| 阻塞原因 | 环境、数据、需求或系统阻塞 |

### 6.7 自动化中心

自动化中心建议优先支持 Web UI 自动化和 API 自动化。

核心能力：

- 从测试用例生成自动化脚本。
- 脚本在线查看和版本管理。
- 执行计划配置。
- 定时回归。
- 失败截图、页面 HTML、trace 记录。
- 日志分析。
- 失败归因。
- 元素定位建议和自修复。

推荐技术结构：

```text
tests/
pages/
data/
conftest.py
pytest.ini
reports/
```

脚本生成建议：

- Web UI 自动化优先使用 Playwright。
- 接口自动化优先使用 pytest + requests 或 HTTPX。
- 页面行为采用 Page Object 封装。
- 测试数据采用 JSON、YAML、CSV 或数据库准备。
- 断言要明确，失败要保存截图、HTML 或 trace。

### 6.8 缺陷中心

缺陷中心负责缺陷的创建、流转、关联和分析。

AI 自动生成缺陷时，建议字段：

| 字段 | 说明 |
|---|---|
| 缺陷标题 | 简明描述问题 |
| 所属模块 | 问题所属业务模块 |
| 严重程度 | 致命/严重/一般/轻微 |
| 优先级 | P0/P1/P2/P3 |
| 复现步骤 | 可按步骤复现 |
| 实际结果 | 当前系统表现 |
| 预期结果 | 正确系统表现 |
| 环境信息 | 浏览器、设备、版本、接口环境等 |
| 截图/日志 | 失败证据 |
| 关联用例 | 来源测试用例 |
| 关联需求 | 来源需求编号 |

### 6.9 报告中心

报告中心用于自动生成测试过程和测试结论文档。

报告类型：

- 测试日报。
- 回归测试报告。
- 版本测试报告。
- 自动化执行报告。
- 缺陷趋势报告。
- 质量风险报告。

AI 报告应总结：

- 本轮测试范围。
- 执行完成情况。
- 用例通过率。
- 缺陷分布。
- 严重问题说明。
- 阻塞问题。
- 遗留风险。
- 是否建议上线。

### 6.10 知识库

知识库用于沉淀企业测试资产。

沉淀内容：

- 历史需求。
- 历史测试点。
- 历史测试用例。
- 历史缺陷。
- 自动化脚本。
- 执行日志。
- 缺陷分析经验。
- 业务规则说明。

AI 可以基于知识库做相似需求检索、历史缺陷提醒、用例复用建议和回归范围推荐。

## 7. AI 能力设计

平台不应只设计一个大模型入口，而应设计多个专职 AI Agent。

| Agent | 职责 |
|---|---|
| 需求解析 Agent | 解析文档、提取功能点、识别业务规则和待确认问题 |
| 测试设计 Agent | 生成测试点、测试用例和测试数据 |
| 用例评审 Agent | 检查遗漏、重复、不可执行和预期不清 |
| 自动化 Agent | 生成和维护自动化脚本 |
| 执行分析 Agent | 分析失败日志、截图、接口响应和 trace |
| 缺陷生成 Agent | 生成标准缺陷单 |
| 报告 Agent | 生成日报、回归报告和版本测试报告 |
| 回归推荐 Agent | 根据变更影响推荐需要执行的用例集 |

## 8. 关键闭环链路

平台必须打通以下追溯链路：

```text
需求 → 测试点 → 测试用例 → 执行记录 → 缺陷 → 回归记录 → 测试报告
```

这条链路是后续实现需求覆盖率、用例覆盖率、缺陷密度、自动化覆盖率、回归推荐和质量风险分析的基础。

## 9. MVP 建议

第一版建议聚焦“需求文档 → AI 测试设计 → 用例管理 → Excel 导出”。

必须包含：

- 项目管理。
- 文档上传。
- AI 需求解析。
- AI 测试点生成。
- AI 测试用例生成。
- 用例在线编辑。
- 用例评审状态。
- Excel 导出。

暂不做：

- 自动化脚本执行。
- 缺陷系统深度集成。
- CI/CD 编排。
- 复杂权限模型。
- 脚本自修复。

## 10. 后续演进路线

| 阶段 | 目标 | 关键能力 |
|---|---|---|
| MVP 1 | 建立 AI 测试设计入口 | 文档上传、需求解析、测试点生成、用例生成、Excel 导出 |
| MVP 2 | 建立测试执行闭环 | 用例执行、缺陷生成、执行统计、测试报告 |
| MVP 3 | 建立自动化能力 | Playwright 脚本生成、API 自动化、自动化任务执行 |
| MVP 4 | 建立智能质量分析 | 失败归因、日志分析、回归推荐、质量风险预测 |
| MVP 5 | 建立企业知识库 | 历史资产复用、相似缺陷检索、组织级测试知识沉淀 |

## 11. 核心竞争力

平台的核心竞争力不是简单生成几条测试用例，而是把测试经理、测试工程师和自动化工程师日常重复的分析、设计、执行和归档工作，用 AI 串成一个可追溯、可复用、可持续演进的质量闭环。
