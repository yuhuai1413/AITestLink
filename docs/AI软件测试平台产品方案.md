# AITestLink AI 软件测试平台产品方案

> 更新时间：2026-07-18

## 1. 产品定位

AITestLink 是面向测试团队、研发团队和质量管理人员的 AI 软件测试平台。平台不是单点的“AI 生成测试用例工具”，而是围绕真实测试过程，把需求、环境、系统页面、测试点、测试用例、自动化脚本、脚本执行、测试数据汇总和文档生成串成完整闭环。

平台当前定位为完整前后端系统，支持本地开发、后端 API、前端工作台、AI 模型配置、文档模板配置和自动化执行能力。

## 2. 解决的问题

传统测试工作中常见问题：

- 需求文档内容多，人工拆解耗时。
- 测试点和测试用例依赖个人经验，覆盖率不稳定。
- 需求、测试点、用例、脚本之间缺少追溯。
- AI 生成结果如果不评审，容易把错误传递到后续环节。
- 自动化脚本常因定位器、登录页、验证码、页面结构不一致而失败。
- 文档报告常被模型自由生成破坏模板样式，难以对外交付。

AITestLink 的核心方案是：用 AI 提升分析和生成效率，用评审门禁和数据追溯保证质量，用系统识别和模板填充降低自动化与文档生成的不确定性。

## 3. 目标用户

| 角色 | 关注点 | 平台价值 |
|---|---|---|
| 测试经理 | 覆盖率、风险、进度、交付物 | 查看项目全链路状态，控制评审和文档交付 |
| 测试工程师 | 需求拆解、用例设计、执行记录 | 快速生成测试点和用例，减少重复劳动 |
| 自动化工程师 | 脚本生成、运行稳定性、失败定位 | 借助系统识别和执行日志优化脚本 |
| 产品/业务人员 | 需求覆盖、待确认问题 | 参与需求确认和测试范围评审 |
| 项目负责人 | 质量结果、上线依据 | 获取测试汇总和标准文档 |

## 4. 当前业务闭环

```text
项目创建
→ 输入资料上传
→ 需求解析
→ 环境配置
→ 系统识别
→ 测试点生成
→ 测试点评审
→ 测试用例生成
→ 用例评审
→ 自动化脚本生成
→ 脚本评审
→ 可视化执行脚本
→ 数据汇总
→ 测试总结
→ 文档生成
```

其中“评审通过”和“数据有效”是核心门禁。没有通过评审的数据不能进入下游生成；上游重新生成后，下游数据会被标记失效，防止失去来源依据。

## 5. 核心模块

### 5.1 首页驾驶舱

展示项目数量、测试状态、执行趋势、质量指标和待处理事项，给管理者提供质量入口。

### 5.2 项目空间

项目空间是完整测试流程的主工作台。主要页面包括：

- 概览
- 输入资料
- 环境配置
- 需求列表
- 测试点
- 测试用例
- 自动化脚本
- 执行脚本
- 数据汇总
- 测试总结
- 文档生成

讲解时可以强调：这不是几个孤立页面，而是一条从需求到交付物的流水线。

### 5.3 输入资料

支持上传需求文档、接口文档、Excel、PDF、Word、Markdown 等资料。输入资料是后续需求解析的来源。

删除输入资料会影响后续链路，因此平台会提醒并处理下游数据，避免测试点、用例和脚本脱离原始资料。

### 5.4 需求解析

AI 从文档中提取：

- 需求编号
- 模块
- 功能点
- 来源
- 风险等级
- 业务规则
- 待确认问题

需求必须经过评审，评审通过后才能生成测试点。

### 5.5 环境配置与系统识别

环境配置支持：

- Web / APP 环境类型
- 访问地址
- 测试账号
- 默认环境
- 登录验证码策略
- 超时时间和重试次数

系统识别借助 AI 和浏览器自动化能力，在限定需求范围内识别相关页面、表单、按钮、输入框、菜单和潜在阻塞点。它的目标不是盲目扫描所有页面，而是为后续自动化脚本生成提供真实页面上下文。

### 5.6 测试点生成

AI 根据已评审需求生成测试点，覆盖：

- 正常流程
- 异常流程
- 边界值
- 权限控制
- 数据一致性
- 状态流转

测试点必须保留需求关联，不能生成无法追溯来源的测试点。

### 5.7 测试用例生成

AI 根据已评审测试点生成可执行测试用例。用例字段包括：

- 用例编号
- 模块
- 测试点
- 用例标题
- 优先级
- 前置条件
- 测试步骤
- 测试数据
- 预期结果
- 测试端
- 测试地址
- 所需角色
- 自动化标识
- 评审状态

用例必须经过评审后，才能进入自动化脚本生成和文档生成。

### 5.8 自动化脚本

AI 根据测试用例、环境配置、账号信息和系统识别结果生成自动化脚本。脚本生成重点不是“写出代码”，而是保证：

- 定位器贴近真实系统元素。
- 登录流程和验证码策略可配置。
- 不是登录成功就判定测试通过。
- 必须执行测试用例中的功能步骤和断言。
- 失败时输出可理解的失败摘要。

### 5.9 可视化执行

支持以 headed 浏览器方式执行脚本，便于观察浏览器真实行为。执行链路会记录：

- 执行状态
- 执行日志
- 失败摘要
- 原始错误
- 脚本结果

### 5.10 数据汇总

数据汇总页用于展示从上游流转而来的测试数据状态，不在这里重新评审。评审状态来源于需求、测试点、用例、脚本等前置环节。

### 5.11 文档生成

平台支持上传 Word 文档模板。系统会解析模板结构，并在生成时复制原始模板，按占位符和表格结构填充当前项目数据。

这个设计避免了模型自由生成文档导致模板格式破坏的问题，目标是实现“像复制模板文件，然后替换当前项目数据”。

## 6. AI 在各环节的应用

| 环节 | AI 作用 | 质量控制 |
|---|---|---|
| 需求解析 | 从文档提取模块、功能、规则、风险和问题 | 输出结构校验，人工评审 |
| 系统识别 | 识别相关页面、元素、登录阻塞和交互路径 | 限定需求范围，记录识别过程 |
| 测试点生成 | 基于需求生成覆盖场景 | 必须关联需求，结构校验 |
| 测试用例生成 | 生成步骤、数据、预期和角色 | 必须关联测试点与需求，评审门禁 |
| 自动化脚本生成 | 根据用例和页面识别结果生成脚本 | 不能只登录，必须执行功能断言 |
| 执行分析 | 将底层异常转换为用户可理解的失败摘要 | 保留原始错误 |
| 文档生成 | 在模板缺失时辅助生成内容；有模板时主要做结构填充 | 优先确定性模板渲染 |

## 8. 产品优势

- 覆盖测试全流程，而不是单点生成。
- 每个阶段有明确输入、输出和评审门禁。
- 数据链路可追溯，能解释每条用例来源。
- 自动化脚本结合真实系统识别结果，减少定位器不准的问题。
- 文档生成尊重用户模板格式，适合正式交付。
- 错误提示面向用户可理解，降低排查成本。
